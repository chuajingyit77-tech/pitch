# 给 Papu 的实施说明

> 目标：8 周内上线一个 5 人真的每天在用的系统。
> 不是做一个功能齐全的系统 —— 是做一个**会被用**的系统。

---

## 技术选型（已定，不要重新讨论）

| 层 | 选择 | 为什么 |
|---|---|---|
| 后端 | **Supabase**（托管 Postgres + Auth + Storage + RLS） | 你一个人，不要做运维。RLS 让权限落在数据库层，前端写错也漏不出去 |
| 前端 | 单页应用 + Tailwind（或原生 CSS 变量），响应式 + PWA | 一个人能维护 |
| 部署 | Vercel / Netlify 免费层 | |
| 认证 | Supabase Auth **邮箱魔法链接** | 5 个账号，不要让同事记密码 —— 记密码就会不用 |
| 文件 | Supabase Storage，bucket `evidence` | |
| AI | Claude API，**只用三处**：交付描述归类到收入线、提示缺什么证据、生成每周六问 | 用量极小，不要做自主 Agent |

**不要引入**：自建认证、自建文件服务、Redis、微服务、状态管理库、原生 App、WhatsApp Business API。

## 五条实现纪律

1. **验收标准不可为空。** 数据库已有 `check` 约束。前端也要挡 —— 派不出没有验收标准的活。
2. **member 不能自我验收。** RLS 策略 `member_update_own_deliv` 的 `with check` 已限制只能改成 `submitted`。前端不要给验收按钮。
3. **前端不算钱。** 跑道、健康度都读视图（`v_runway`、`v_project_health`）。同一个数字有两个算法，就一定会有一天对不上。
4. **提交流程计时。** 在「我的今天」埋一个计时，从打开到提交成功。**超过 60 秒就是设计失败，不是用户懒。**
5. **不做扣分和排名。** 会引发对抗性填报。只显示，不惩罚。
