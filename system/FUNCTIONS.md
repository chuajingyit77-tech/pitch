# JY 集团运营系统 — 功能清单

> 依据：《蔡景昱个人与集团总档案》v1.0，资料截止 2026-08-24
> 决定：预算 RM15,000–30,000｜日常用户 JY + 核心 4 人｜第一版目标「管住人的交付」

---

## 0. 一句话定位

**这不是一个 dashboard，是一台把模糊活动转成「可验收成果 → 付款节点」的机器。**

你自己在第 15 节写下了诊断：

> 「我的问题不是完全没有资源，而是这些资源尚未被压缩成清晰的产品、合同、付款节点和负责人。」

系统的全部功能都从这一句推导。

### 一个必须先说明的设计决定

你选了「管住人的交付」作为第一版目标。这和你的自我诊断一致（"员工依赖指示、项目证据不足"），我认可。

但单独做会失败：**5 个人勤奋地交付一堆没人付钱的东西，只会让烧钱更清楚。**

所以本设计的结构是：**交付是主对象，但每一条交付强制挂在四条收入线之一，并强制带证据。** 在数据库层面，`deliverable.revenue_line_id` 是 `not null`。管人和要钱因此是同一个功能，不是两个互相抢资源的功能。

## 1. 必须有的功能（第一版做）

### ① 我的今天 — 核心 4 人唯一会打开的页面

| 功能点 | 为什么必须 |
|---|---|
| 只显示自己本周的 2–3 件事 | 全景对员工是噪音，且会暴露现金与薪资 |
| 每件事显示**验收标准**（"完成长什么样"） | **这是治"员工依赖指示"的真正解药：不是给指示，是给验收标准** |
| 提交 = 拍照 + 一句话，目标 < 30 秒 | 超过 60 秒员工必然退回 WhatsApp |
| 「我被卡住了」按钮 → 自动生成一条你的决策 | 把阻塞从私聊变成有记录、有计时的队列 |

### ② 交付看板 — 你的主屏

| 功能点 | 为什么必须 |
|---|---|
| 5 列 = 5 个人，本周交付与状态 | 一眼看完全组 |
| **你在这个屏上只有两个动作：验收 / 打回** | **刻意不放"我来做"按钮 —— 用界面强制你从执行者变回验收者**，直接对应你写的"每周只处理决策清单，不代替员工做执行" |
| 逾期自动标红；连续两周零交付自动升级到决策队列 | 不需要你记得去追 |

### ③ 决策队列 — 48 小时 SLA

| 功能点 | 为什么必须 |
|---|---|
| 每条带：金额、截止日、**建议选项 A/B/C**、谁在等、已等多久 | 解决"所有决定回到我身上"的方法不是减少决策，是让决策**排队、计时、带建议** |
| 超 48 小时变红置顶 | 你的组织风险里最贵的一项是决策延迟 |
| 显示"这笔钱影响跑道 X 天" | 让每个决策自带现金后果 |

### ④ 收入线与付款节点

| 功能点 | 为什么必须 |
|---|---|
| 四条收入线各一张卡（Blek 止血 / HDJ / 工厂数字化 / 大型项目） | 你第 10 节自己定的四条主线 |
| **项目强制四字段：谁付款、预算来源、下一个收钱动作、Gate 日期** | 缺任一 → 数据库生成列 `has_payment_path = false` → 自动标灰。**直接回答你写的"不清楚最接近收费的三个项目是什么"** |
| 证据等级 V / S / C / M 内建为字段 | 沿用你已有的方法论 |

### ⑤ 现金与跑道

| 功能点 | 为什么必须 |
|---|---|
| **一个大数字：距离 RM1,000,000 防线还有几个月** | 你有现金也有月烧，**从来没把两者连成一个数字** |
| 个人 vs 公司开支分列 | 你的待补事项第 2 条。不分账，这一屏就是假的 |
| 支出试算滑块：拖动看跑道减少几天 | 让"这笔支出值不值"变成可看见的，而不是感觉 |

### ⑥ 证据 — 嵌在上面各处，不是独立模块

员工在提交交付时顺手上传，**不需要"去证据室"**。你的 8 个文件夹（01 Corporate … 08 People）是聚合视图，不是入口。

### ⑦ 每周六问 — 一页纸

你第 12 节的六个问题，由系统按当前数据自动作答。**周会只看这一页。**

## 2. 不必要的功能（第一版明确砍掉）

| 你档案里列了/想要的 | 决定 | 理由 |
|---|---|---|
| **WhatsApp Business API** | **砍** | 你自己写"仍处于计划阶段"。需 Meta 审核 + BSP 代理商 + 月费，对 5 个用户是严重过度工程。**替代：WhatsApp 群里发一条链接，点开就是「我的今天」——一模一样的员工行为，零集成成本。这一项省下的钱和时间最多。** |
| **语音输入** | **砍**（v2 再加） | 浏览器原生 Web Speech API 后加只需几十行代码。不要为它提前买硬件。 |
| **Proposal 自动生成模块** | **砍** | 零付费客户时，生成再多提案不产生现金。 |
| **Mac Mini + 大显示屏** | **延后到第一笔真实收款之后** | 这是仪式感支出。你现在站在现金防线上。现有电脑 + 一个网页足够。预算里保留，但不先花。 |
| **Blek Exit 独立模块** | **砍** | 它是 `project` 表里 `revenue_line_id = 'blek'` 的几行。做成独立模块会让 Papu 把同样的 CRUD 写三遍。 |
| **HDJ 独立模块** | **砍** | 同上。 |
| **完整 HR / 考勤 / 薪资** | **砍** | 只需要"本周交出了什么 + 证据"一栏。 |
| **多级权限与审批流** | **砍** | 5 个用户。只要两种角色：owner（你，全部）、member（只看自己 + 收入线只读）。 |
| **原生移动 App** | **砍** | 响应式网页 + 加到手机主屏幕（PWA）即可。Zam 在工地、Liong 在带看，用的都是浏览器。 |
| **自主 AI Agent 跑业务** | **砍** | 第一版的 AI 只做三件小事：交付描述自动归类到收入线、提示缺什么证据、生成每周六问。不做自主 Agent。 |
| **其余 4 人纳入系统**（Zam / Venice / Nazrul / Arcel） | **砍** | 你档案里这四位的长期去留尚未确认。现在纳入是浪费。 |

## 3. 你没列、但必须补上的功能

| # | 功能 | 为什么 |
|---|---|---|
| 1 | **跑道计数器**（现金 ÷ 月烧 = 一个数字） | 你有两个数，从没连起来。**按你的档案，防线以上可用 RM0 —— 跑道是 0.0 个月** |
| 2 | **自动 Kill Rule** | 项目超过 N 天无 Gate 或缺付款人 → 自动标红建议暂停。规则是你自己的，但**必须由系统自动执行，否则永远不会执行**（已写成 `v_project_health` 视图） |
| 3 | **个人 vs 公司开支分账** | 你的待补事项第 2 条。不做这个，现金屏是假的（`entity.is_personal` 字段） |
| 4 | **验收标准为必填字段** | 数据库层 `check (length(trim(acceptance_criteria)) >= 10)`。派不出没有验收标准的活 |
| 5 | **周对比（本周 vs 上周）** | 没有对比就没有进步感，这是采用率的关键（`deliverable.week_of` 字段） |

## 4. 让人"想用"的真正机制

美观是必要条件，不是充分条件。对一个 5 人、零收入、老板亲力亲为的团队，驱动日常使用的是行为设计：

1. **你的周会只看这个系统。不在系统里的东西不被讨论、不被认可。** ← 唯一真正有效的机制，其余都是辅助
2. **提交成本 < 30 秒。** 超过 60 秒必然退回 WhatsApp
3. **每人只看自己那一栏。** 全景只有你看
4. **即时反馈**：交付提交后当天能看到你验收/打回的状态变化。**沉默的系统会死**
5. **第一版不做扣分与排名。** 会引发对抗性填报（编假数据）。只显示，不惩罚

### 视觉与交互
- 深浅双主题（工地日光下必须能看清，这不是可选项）
- 移动端优先，底部标签栏，可加到手机主屏幕
- 数字用等宽字体对齐；跑道条上"现金防线"是一条实体刻线
- 中英混排，符合团队实际语言习惯

## 5. 预算与时间线

### 预算分配（RM15,000–30,000）
| 项目 | RM |
|---|---|
| 外部前端/设计支援 6–8 周（这是让它"好看"的钱） | 8,000–15,000 |
| Supabase Pro + Vercel + 域名 + Claude API 首年 | 2,500–3,500 |
| 硬件 Mac Mini + 显示屏（**挂到第一笔收款之后**） | 6,000–9,000 |
| 缓冲 15% | — |

Papu 的工时已在薪资内（RM2,500/月），不额外计。

### 硬性上线闸门

你自己的警告：**"没有预算上限，需求会不断扩大，系统会一直开发却无法上线。"** 因此设死闸门：

| 周 | 交付 | 闸门 |
|---|---|---|
| 1 | 数据模型 + 5 人的交付定义与验收标准 | 模型冻结，之后改动需你书面批准 |
| 2–3 | **只做「我的今天」+「交付看板」并上线** | 不做第三个屏 |
| 4 | 真人跑满一周 | **不达标就不准写第三个屏** |
| 5–6 | 决策队列 + 收入线 | |
| 7–8 | 现金跑道 + 每周六问 | |

**MVP 验收标准（不满足即停止追加投入）：**
连续 2 周，5 人每人每周提交 ≥2 条带证据的交付，且**你的周会只看系统、不看 WhatsApp**。

## 6. 上线前必须补的数据

这些不阻塞原型，但**阻塞上线**：

1. 5 位核心成员各自的**周交付定义与验收标准** —— 只有你能定，无法外包
2. 各主体最新银行余额，与**个人/公司开支的准确拆分**（待补事项第 2 条）
3. 四条收入线当前各自的 **Next Paid Step 与证据**（待补事项第 7、8、9 条）

**在第 2 项补齐之前，现金屏的"真实月烧"只能当估算用，不能当事实用。** 系统里已经这样标注了。
